# Stocks — Owner's Earnings DCF Sweep

Andrew's project (started 2026-10-12): screen the Russell 3000 for stocks that can clear his hurdle rates.

## Scope
- Universe: top 3,000 US-listed operating companies by market cap (free reproducible Russell 3000 equivalent — see `universe_notes.md`), filtered to **market cap < $40B**.
- Size on 2026-10-12: **2,617 companies** (`universe.csv` / `queue.json`). APP is the pilot and an exception — its market cap is >$40B, it stays as the worked example only.
- Cadence: two pass-1 workers (`dcf-hourly-sweep`, `dcf-sweep-parallel` — the names are historical) each firing every 15 minutes; measured throughput is what matters (audit round 1: ~1.7 companies/hour). Full sweep: weeks, not days. A daily HTML ranking is sent once a day (`dcf-daily-ranking`, ~7pm ET) built from whatever is completed so far — it gets more useful every day, it is not held until the sweep finishes.
- Queue order: Andrew's watchlist (under $40B) first, then descending market cap. A universe rebuild (`build_universe.py`) keeps every surviving name's queue entry verbatim (status, claim stamp, completion date, notes); only the order changes.

The SEC files go through `_stable.py`, which leaves a file untouched when nothing but its run date would change, so a file's `as_of` is the day its content last changed. ## v5 tooling (2026-10-13; round-2 hardening 2026-10-14)
- `queue.py claim|done|block|requeue|reap` — the ONLY way workers touch `queue.json`: file-locked (`_lock.py`: fcntl, or msvcrt on Windows), atomic writes, 90-minute claim lease. `claim` runs the reaper first, under the same lock (round-2: no job ever called reap, so crashed claims stuck forever). `block <TICKER> --stdin` reads the reason from stdin (a quoted shell argument mangles `$` amounts); a reason starting with `DATA_GAP` lands in the separate `blocked_data_gap` status — the list awaiting override decisions — vs `blocked_no_data` for filings that don't exist yet.
- `ttm.py <TICKER>` — TTM owner's earnings (OCF, capex, SBC, diluted shares) computed in code from EDGAR 10-Q YTD facts (FY − prior YTD + current YTD), JSON out with every input shown, and the same JSON saved to `<TICKER>/ttm.json` as the base pin's provenance. Agents never hand-compute TTM again. Day counts are inclusive (a filled annual leg is exactly the override value, matching the engine); leg matching tolerates start dates shifted a few days; a never-filed capex hard-blocks (exit 3) unless an override fills it — no more zero-fill-with-warning.
- `make_score.py <TICKER>` — builds `score.json` (above). Refuses when `dcf_numbers.json` has a `data_gap`, when judgment/probabilities don't match the engine run, or when a tier override lacks a reason — and (round-2) when the engine output is pre-v5, when its `content_hash` is missing/mismatched, when an override is negative or out of band without an `ack_reason`, when a pinned base differs from `ttm.json` by >0.1% without a declared `base_override`, when a 20-F/40-F filer has no applied `ads_ratio`, or when `in_scope_under_40b` contradicts the computed market cap. Confidence is clamped to medium under WIDE_SCENARIO_SPREAD (`confidence_capped: true`). v5.5 adds refusals for a declared `share_class_mismatch` and (verifier round) a malformed one — a string, number or list, an object whose `value` is not a bool, or any non-empty object without `value` —, an override `currency` other than "USD" (or "USD" on a kind other than "filing"), a USD declaration the engine run FX-converted anyway, an applied kind "filing" override the engine used verbatim as USD through the last-filed-unit fallback without an explicit `currency: "USD"` (HTHT; that is every use of the fallback by a filing override — kind "estimate" is exempt), and a `capex_override` still declared beside `OVERRIDE_SUPERSEDED_BY_FILED_TAG:capex` (WY); for pre-5.5 ADS output the scope is checked on the corrected cap (price × `shares_diluted_latest` ÷ `ads_ratio`), and judgment.json's scope is rewritten when it still holds the scope the old cap implied.

**Override registry** (`_system/overrides_registry.json`, written only by `make_score.py`): on every score, the ticker's entries are **replaced wholesale** and re-derived from that run (round-2: the old upsert left stale entries behind when an override was removed). Since the engine 5.5 re-score an entry whose declaration is unchanged keeps the `date` it was first recorded (the value / kind / source / reason of a field override; the declaration fields of an event — a `base_override` that only gains its missing `kind` keeps its date too); the measured impact is re-derived every run, and a new or changed declaration takes the day's date. **[Codex, PR #31]** Every material field is part of that identity: a field override's `currency` (now written into its entry when declared — USD verbatim vs FX conversion) and `scope`, and a base_override's `kind`, payable / amortized shape (`basis`, `figures`, `shares`) and (v5.6) `native_base`; the only allowance is that a pre-5.5 base_override event, which never recorded `kind`, is matched on its other fields. Before, every score re-dated every entry of the ticker, so a re-score rewrote when an override was first taken (NTNX's 2026-10-15 `base_override` and WF's 2026-10-16 `ads_ratio` read 2026-10-19). One entry per (ticker, field) for every judgment override the engine applied, carrying the override itself (value, kind, source, reason, date) and its measured impact **on the base the final run actually used**. The registry also records every other judgment call a run embodies, each as an entry with an `event` field: `tier_override` (with tiers + reason — the ranking badges these on the row and detail page), `manual_price`, `base_override`, `gterm` (non-default terminal growth), `cik` (non-default CIK), `ads_ratio`, (v5.5) `scope_correction` (`old_cap`, `new_cap`, `in_scope`: the pre-5.5 ADS market-cap correction decided the scope), and (v5.6, Codex review round 8 of PR #47) `iprd_deferred_payment` (one per deal: `deal`, `first_charged_period`, `contingent_total`, `paid_to_date`, `periods` — every period ever declared, carried across runs, its recorded amount immutable (Codex review round 10): the prior events are read before the wholesale replace and merged, so the only memory of a paid milestone survives its judgment.json entry being deleted). Each entry records `base_used` — `"ttm"` when the score's base was a TTM pin via `--base-oe-ps` / `--ttm`, `"payable_5y"` when it was the insurer payable-earnings pin via `--base-judgment` (base impact zero by construction; the IRR counterfactual replays the same pin with field overrides off), (v5.5) `"declared_pin"` when it was a `--base-oe-ps` pin equal to a declared `base_override` (no `basis`, or (v5.6) `basis` `iprd_amortized` on the median native base) and not ttm.json's figure (an `iprd_amortized` pin on native base `ttm_json` is ttm.json's TTM base less the amortization: `"ttm"`, on its `base_override` event too) — measured the same way as the payable pin, never by re-running ttm.py (before 5.5 such a pin went through the TTM branch, which an IFRS filer cannot run: VIV refused) — else `"median_3y"` — plus the base OE/share without → with the override on that basis, the % change in the base, the weighted IRR without → with and its change in percentage points, all measured on the final run's exact configuration (same moat/probs/offsets/mults/gterm and the same base pin) with only the overrides toggled off, and `unblocks_tier`: true when the override covers a data gap in the last 3 fiscal years, i.e. it is the only reason the company has a tier at all. `unblocks_tier` entries are the judgment calls that matter most, however small the dollar effect — review those first. The identical block is stored in `score.json` as `override_impact` and rendered on the company's page in the daily ranking; the engine's own `dcf_numbers.json` impact block is measured on the engine-native base and is NOT the headline figure when a TTM pin is in force. v5.5: on engine output from another release the impact is never re-measured through the current engine — the prior score.json block is carried when it was measured on the same base (`impact_carried_from_prior_score`, `counterfactual_engine_release`), otherwise the impact fields are null with a "not measured" note. The same holds (verifier round) for the insurer payable pin's own impact on the `base_override` event: carried from the prior registry event when that was measured on the same pinned base and weighted IRR (4 dp), otherwise null with the "not measured" note, labelled `base_used` `payable_5y` either way; and every measurement runs before make_score's first write.

## Scenarios, probabilities, and the moat-driven fade (v3, 2026-10-12)
- **Five scenarios** every time: super bear, bear, base, bull, super bull — each with an assigned likelihood (must sum to 100%). Defaults 10/25/30/25/10, growth-start offsets −12/−5/0/+5/+12pp vs the capped historical base growth, owner's-earnings level multipliers 0.75/0.90/1.00/1.10/1.25. The agent may skew probabilities (and, with a written reason, offsets/multipliers) to the company's evidence. The headline value is the **probability-weighted** IV/IRR from the probability-weighted cash-flow path.
- **Moat score 0-10, justified in writing** (specific pillars FOR, specific erosion forces AGAINST — no generic claims). Rubric: 9-10 wide/durable, 7-8 strong, 5-6 moderate/narrow, 3-4 weak, 0-2 none.
- **The moat sets the fade.** Growth fades linearly from the scenario start rate to the 2.5% terminal rate over the Competitive Advantage Period **CAP = clamp(2 + 1.3 × moat, 2, 15) years** — moat 0 fades in ~2 yrs, moat 5 in ~8.5 yrs, moat 10 gets the full 15-yr projection. A high starting growth rate with a low moat score gets faded hard, by design.
- Workflow per company: preliminary engine run → research → score moat + set probabilities → final engine run with `--moat --probs [--offsets --mults]`.

## Scoring — hurdle tiers (probability-weighted implied IRR from the owner's-earnings DCF at current price)
- **S: ≥25%** — exceptional
- **A: 20–25%** — clears the 20% level
- **B: 15–20%** — clears Andrew's 15% hurdle
- **C: 10–15%** — below hurdle
- **D: <10%**
- **F: no positive conservative owner's earnings on the base actually used** (the 3-yr median, or the TTM pin) — a DCF on owner's earnings can't support any hurdle; flagged, not forced. v5.4 splits it: `sbc_exceeds_cash` (OCF − capex is positive but SBC consumes it) vs `no_cash_generation`.
- **Band (v5.4):** the bear-case and bull-case tiers are reported next to the headline (`tier_bear` → `tier_bull`); when they differ the run carries `TIER_BAND` and any position is sized to the bear end. The headline stays the weighted IRR.

The engine's tier is the *starting* point. The analyzing agent may move the final tier in `score.json` **only** with a written reason in `analysis.md` (e.g. historical growth was one-off, capex is really all maintenance, balance-sheet risk). Numbers tier and final tier are both kept.

## Owner's earnings definitions (standardized, see `dcf_engine.py`)
- Conservative: Operating Cash Flow − total capex − stock-based comp.
- Acquired in-process R&D (v5.6): expensed at acquisition; where the cash-flow statement adds it back in OCF and pays it in investing (the us-gaap cash tag, or the worker's `iprd_cash_flow_check` citing the lines), no OE leg sees it — it is deducted ONCE from every intrinsic value and added to the IRR price (`iprd_adjustment`), never from the base; paid inside OCF (NBIX) it is already in OE and not deducted; impairments of capitalized intangibles are not deducted; a declared deferred payment of an earlier deal (`iprd_deferred_payment`) is deducted but does not count toward recurrence (Fixes & lessons, Engine 5.6).
- Maintenance version: Net income + D&A − min(capex, D&A) − increase in net working capital (ex cash/debt).
- SBC is always treated as a real cost in the conservative/base case.

- **2026-10-19 — Insurer payable-earnings base (Andrew's decision, after RNR).** The 2026-10-15 one-notch softening assumed the OCF base at an insurer is somewhat inflated. RNR showed it can be off by more than 2×: the engine's median base was $77.78/sh (FY2025 OCF $3,693,107,000 includes a $998,854,000 reserve build and the cash earned by the consolidated Capital Partners vehicles, of which $935,409,000 of FY2025 net income belongs to redeemable noncontrolling interests), while operating income available to common shareholders — the payable-earnings line the filer prints every quarter — averaged $1,264,683,400 over FY2021–2025 ($81,599,000 / $322,791,000 / $1,824,910,000 / $2,234,426,000 / $1,859,691,000), i.e. $27.21/sh on 46,483,000 diluted shares. Tier S by numbers, softened to A, where the payable base prints C. Rule (WORKER_SPEC.md step 4, AGENTS.md "Sector misfits"): a P&C insurer or reinsurer that prints operating income available to common declares a filing-kind `base_override` = average of the last five FY of that line ÷ latest diluted shares, construction quoted in analysis.md; the one-notch `tier_override` is then not applied; alert suppression and low confidence stay. Five-year average rather than 3-year median because a cat cycle is longer than three years. Filers without the line (life, banks, REITs) keep the 2026-10-15 rule. Mechanics (Codex's review of PR #8 found the spec-only version unenforceable: a declared base changed nothing unless the worker typed `--base-oe-ps`, make_score routed every pin through the TTM counterfactual, which fails at any filer without a TTM, and an ADS filer's per-ordinary figures would have met a per-ADS price unscaled): `dcf_engine.py --base-judgment` reads `base_override {basis: payable_earnings_5y, kind: filing, figures[5], shares, value, source, reason}` from judgment.json, recomputes the base (`payable_base_per_share`), scales it by `ads_ratio`, refuses (BAD_BASE_OVERRIDE, exit 3) a declaration that does not reproduce, a `shares` that is not the run's latest diluted count, or an FX-converted filer, records `payable_base` in dcf_numbers.json with `base_source: judgment_base_override`, and `_measure_run` drops the flag like `--ttm`. `make_score.py` validates the shape, measures impact on a `payable_5y` basis (base impact zero by construction; the IRR counterfactual replays the same pin with field overrides off, a replay gate reading as an honest null when the override unblocks the tier), checks provenance figure for figure against `payable_base`, refuses the one-notch `tier_override` on top of the base (double-counting), carries basis / figures / shares / SIC into the registry event together with the pin's own measured impact (engine-native median base and IRR with field overrides on → pinned payable base and IRR, tiers both ways — Codex round 3), and prints the five exact figures in key_numbers.md so analysis.md quotes them from there. ## Method honesty
- This is a *screening* DCF: one standardized growth-fade model for every company so rankings are comparable. It is not a bespoke institutional model per name.
- Maintenance capex is estimated, never disclosed — hence the two definitions and a range mindset.
- Financials (banks/insurers) and REITs: owner's earnings / capex logic fits poorly. The agent must flag sector-model mismatch in `analysis.md` and grade confidence low rather than force a tier.
