Run ONE company through the owner's-earnings DCF sweep (v5 method — normalized base, blended growth, moat-driven fade, five scenarios, and a hard DATA GATE: the engine never emits a tier when filing data is missing). Read ~/workspace/stocks/_system/README.md first — including "Fixes & lessons" — and follow it exactly. ~/workspace/stocks/_system/DCF_AUDIT.md explains why each rule exists; the APP pilot folder (~/workspace/stocks/APP/) is the worked example of the required output shape.

MECHANICS (v5 — no exceptions): NEVER edit queue.json or score.json by hand. The queue is managed only through queue.py, TTM figures come only from ttm.py, and score.json is built only by make_score.py from dcf_numbers.json + a judgment.json you write. Hand arithmetic and hand transcription are how v4 produced wrong numbers (see the audit in README "Fixes & lessons").

Steps:
1. CLAIM: run `python3 ~/workspace/stocks/_system/queue.py claim`. It atomically claims the first pending company (fcntl lock, 90-minute lease) and prints its ticker — that ticker is your company. If it prints nothing (no pending entries), rebuild the daily HTML (step 9) and finish silently.
2. Preliminary engine run: `python3 ~/workspace/stocks/_system/dcf_engine.py <TICKER>` (timeout 120s). It writes financials_history.csv and dcf_numbers.json into ~/workspace/stocks/<TICKER>/ from SEC EDGAR filing-direct data: normalized base OE (median of last 3 FY OE/share), blended growth adjusted for share-count trend, two owner's-earnings definitions, diagnostics, fragility_flags, and the per-period tag provenance (capex_tag / sbc_tag columns). EXIT CASES:
   - Exit 4 (prints "DATA_GAP for <TICKER>: ...") → required filing data is missing (SBC, capex, shares, or non-USD reporting currency — see the data_gap list in dcf_numbers.json). Do NOT score it, do NOT try to work around the gap. Block it — the reason goes through stdin, never a quoted shell argument (dollar amounts get mangled): `printf '%s' "DATA_GAP: <fields> — <one-line detail from the DATA_GAP flags>" | python3 ~/workspace/stocks/_system/queue.py block <TICKER> --stdin` and finish. (A reason starting with DATA_GAP lands the entry in blocked_data_gap; anything else lands in blocked_no_data.)
   - Exit 3 with a DATA_GAP line (price-only gap) → same: queue.py block via --stdin as above and finish.
   - Exit 3 NO_DATA / exit 2 NO_CIK (thin/no history, often a holding-company CIK change) → do NOT score it F and do NOT give up immediately: web-search the company's operating-parent CIK ("<company> CIK 10-K") and rerun with `--cik <CIK>`; only if no filing parent exists, run `printf '%s' "NO_DATA: <reason>" | python3 ~/workspace/stocks/_system/queue.py block <TICKER> --stdin` and finish.
3. Research (1-3 web searches): what the business does, latest earnings quarter, TTM results since the fiscal year-end, competitive position, red flags (dilution/SBC load, customer concentration, litigation, going-concern, one-off gains, divestiture/restated basis breaks).
4. ADDRESS EVERY FRAGILITY FLAG in dcf_numbers.json — each one gets a specific resolution in analysis.md, not a wave-off. The recurring ones: STALE_FY (>7 months since FY end) → run `python3 ~/workspace/stocks/_system/ttm.py <TICKER>` — it saves its full output to ~/workspace/stocks/<TICKER>/ttm.json — and pass `--ttm` in the final engine pass so the engine reads the base from ttm.json; quote ttm.json's inputs (FY, prior YTD, current YTD for OCF/capex/SBC/shares) in analysis.md — NEVER compute TTM figures yourself. (--base-oe-ps is legacy-only: make_score.py refuses a pinned base that differs from ttm.json by >0.1% unless judgment.json declares a base_override {value, source, reason}.) If ttm.py exits non-zero, write its message in analysis.md and use the engine's median base instead, with the reason stated. BASE_DIVERGENCE → decide which base is distorted (latest year vs 3-yr median) and say why; use the TTM override or the median accordingly. NI_OCF_DIVERGENCE → find the one-off in the named years (tax deposits, impairments, WC swings). BASIS_BREAK_SUSPECT → identify the divestiture/M&A/restatement and pick growth inputs that don't straddle the break blindly. HIGH_NET_DEBT / BIG_NET_CASH → fold the balance sheet explicitly into the verdict. SECTOR_MODEL_MISMATCH (Finance/Real Estate/Utilities) → confidence low, tier soft.
5. MOAT SCORE (0-10) — score it and justify it in writing. Rubric: 9-10 wide and durable (network effects / high switching costs / structural cost advantage / proven pricing power, high returns on capital held through a cycle); 7-8 strong; 5-6 moderate or narrow; 3-4 weak; 0-2 none. Name the specific pillars FOR and the specific erosion forces AGAINST — generic moat claims are not acceptable. The moat drives the fade: growth holds 2 years, then converges to the 2.5% terminal rate over CAP = clamp(2 + 1.3 × moat, 2, 15) years, 15-year projection (use --gterm only with a written reason, e.g. a structurally declining industry).
6. FIVE SCENARIOS with likelihoods summing to 100%. Defaults: probabilities 10/25/30/25/10; growth-start offsets vs the engine's blended base = -12/-5/0/+5/+12pp; OE multipliers 0.75/0.90/1.00/1.10/1.25. Adjust to THIS company's evidence with written reasons. SANITY CHECK: compare every scenario's growth start against actual recent prints (latest FY, TTM, latest quarter YoY, guidance). A start below what the company just printed — especially bull/super_bull — needs a written reason (guided deceleration, one-off base, basis break); also watch the opposite failure: if the engine's blended growth hit the 35% cap on inflection artifacts (e.g. OE/share CAGR off a tiny base), recalibrate offsets downward with the reason written. FINAL engine pass: `python3 ~/workspace/stocks/_system/dcf_engine.py <TICKER> --moat <score> --probs <5 decimals> [--offsets <5>] [--mults <5>] [--ttm] [--gterm <x>] [--cik <cik>]`. Headline = probability-weighted IV/IRR; tier from weighted IRR (S ≥25%, A 20-25%, B 15-20%, C 10-15%, D <10%, F = no positive normalized OE). If the final pass exits 4 (DATA_GAP), block via queue.py as in step 2 and finish.
7. Write ~/workspace/stocks/<TICKER>/analysis.md in the APP pilot's shape: what it is; owner's earnings (both definitions + which base was used and why, with the ttm.py inputs quoted if a TTM base was used); MOAT section (score, FOR/AGAINST pillar lists, CAP); five-scenario table (likelihood, growth start, OE mult, one-line story, IV@15%, IRR) + weighted result + diagnostics; a FLAGS section resolving every fragility flag; thoughts/overlay including the method range if defensible inputs span tiers, and the price that clears 15% with a margin of safety; final verdict sized to the conservative end when the spread is wide. HARD RULE: every number in analysis.md must be copied from dcf_numbers.json, ttm.py output, or key_numbers.md — never recompute or retype a derived figure (net debt, net income, TTM anything). If a figure you need is not in the computed outputs, say so in words instead of calculating it.
8. Write ~/workspace/stocks/<TICKER>/judgment.json with exactly these fields: name, sector, moat_score (the score from step 5), moat_justification (the written justification), moat_for (list of SHORT pillar strings — the FOR pillars from your MOAT section, one line each, not prose), moat_against (same for the AGAINST pillars), probs_used (the 5 probabilities passed to the final engine run, in super_bear/bear/base/bull/super_bull order), one_liner (quality + moat + why it does/doesn't clear 15% + hurdle-clearing price if below), confidence (low/medium/high — never "high" when WIDE_SCENARIO_SPREAD or unresolved flags are present), tier_override (null, or a tier ONLY when the final tier must differ from tier_by_numbers, with the reason also written in analysis.md), tier_override_reason (required when tier_override is set, else null), in_scope_under_40b. Optional override fields: capex_override / sbc_override / shares_override, each an object {value, source, reason, kind: "filing" or "estimate"}. Overrides are decided by the main agent, not the worker: on DATA_GAP you still block via queue.py with the reason. If judgment.json already contains overrides when you start (a main-agent decision), the engine and ttm.py apply them automatically — proceed normally, carry the override fields into your step-8 judgment.json unchanged, and quote the override and its measured impact in analysis.md. Never invent an override yourself; a gap with no override in judgment.json blocks. Then run `python3 ~/workspace/stocks/_system/make_score.py <TICKER>` — it builds score.json from dcf_numbers.json + judgment.json and REFUSES if they disagree (probabilities/moat not matching the engine run, data gap, override without reason). If it refuses, fix the cause — usually rerun the final engine pass with exactly the judgment inputs — and run it again. One refusal is NOT yours to fix: DATA_GAP:ads_ratio (a 20-F/40-F filer whose judgment.json has no ads_ratio — its per-share figures are per ordinary share while the price is per ADS) → block via queue.py --stdin with that reason and finish; ads_ratio, like the overrides, is a main-agent decision. Never write score.json yourself. make_score.py also writes key_numbers.md (every headline figure from the final dcf_numbers.json) — after it runs, check analysis.md against key_numbers.md and fix any figure that disagrees.
9. Run `python3 ~/workspace/stocks/_system/queue.py done <TICKER>`, then rebuild: `python3 ~/workspace/stocks/_system/build_daily_html.py`.
10. Reporting: silent for routine completions (Andrew gets the daily HTML). Report to chat ONLY if the final tier is S or A (weighted IRR ≥20%): one short line with ticker, tier, weighted IRR, moat, price, weighted IV@15%, one-liner. Also report plainly if the sweep itself is blocked. Never invent numbers — every figure comes from dcf_numbers.json, ttm.py output, or a cited search result.
